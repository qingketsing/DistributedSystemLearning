
# 论文部分

## ZooKeeper: Wait-free coordination for Internet-scale systems 构建于分布式系统之上的应用

### 什么是Zookeeper？

Zookeeper是一个无等待，高性能的协调内核服务。它可以操作像文件系统那样分层组织的简单的无等待数据对象。其设计哲学是不直接在服务端实现复杂原语（如锁），而是提供简单 API，由客户端实现所需原语。

### Zookeeper服务

#### 服务概述

Zookeeper的组织结构是类似文件的Znode，这些Znode是数据对象的抽象。这些Znode既可以像文件夹一样存有子对象，同时也可以像文件一样直接存储数据。ZooKeeper的数据模型本质上是一个具有简化 API 和仅完整数据读取和写入的文件系统。

Znode有两种类型，一种是普通节点，一种是临时节点。同时还有一个监听机制：watch机制。所谓的watch机制，就是当一个节点使用`getData(“/ foo”，true)`的时候，会对foo节点进行监控，当foo节点任务完成后，会告诉这个节点foo已结束，然后开始调用这个节点。这是一个高效、轻量、一次性的“订阅-通知”系统。它让客户端不用傻傻地反复查询，而是被动地等待状态变化的通知，从而极大地提升了分布式系统的效率和响应速度。

#### 客户端API

**`create(path, data, flags)`**：创建在路径path下的znode，data是要存放的数据，并返回新znode的名称。标志flag可以让客户端选择znode的类型：普通的、临时的，并设置顺序标志。

**`delete(path, version)`**： 删除给定路径和版本下的znode。

**`exists(path, watch)`**：如果有路径名路径的znode存在，返回true，否则返回false。watch参数允许客户端在znode上设置监视器。

**`getData(path, watch)`**：返回与znode相关的数据和元数据，如版本信息。watch标志的工作方式与exists()相同()，但是如果znode不存在的话，ZooKeeper就不会设置监视器。

**`setData(path, data, version)`**： 如果版本号是version，写入数据data[]到znode路径。

**`getChildren(path, watch)`**：返回一个znode的子节点集。

**`sync(path)`**：把所有在sync之前的更新操作都进行同步，达到每个请求都在半数以上的 ZooKeeper 服务器上生效。path参数目前没有用。

#### ZooKeeper的保证

ZooKeeper有两个基本的顺序保证： 
1. **线性写**：所有更新ZooKeeper状态的操作是串行的，先来先服务
2. **FIFO客户端顺序**：来自客户端的所有请求按客户端发送的顺序依次执行

对于从传统线性化要求而言，需要逐个完成，示例如下：

```
客户端A: [操作1提交] → [操作1完成] → [操作2提交] → [操作2完成]
```

但是对于A-linearizable（线性一致性模型）而言可以如下：

```
客户端A: [操作1提交] → [操作2提交] → [操作1完成] → [操作2完成]
```

传统分布式互斥锁如 Chubby 提供的锁，可以满足保证互斥访问，但是当执行中宕机时，可能会导致遗留半完成状态。如何在高吞吐（异步流水线操作）与强一致性（顺序保证）之间取得平衡？如何保证 ZooKeeper 数据与外部状态的一致性？  （例如：客户端 A 通过外部通知 B 配置已更新，但 B 的 ZooKeeper 副本可能滞后）这都是zookeeper面临的问题。

对于第一个问题，Zookeeper使用的办法是**Ready Znode 模式**：

```
Leader 操作流程：
1. 删除 /ready → 标记更新开始
2. 更新 /config1, /config2... (异步批量操作)
3. 创建 /ready → 标记更新完成
```

其他进程仅当检测到 `/ready` 存在时，才使用配置。若 Leader 崩溃在步骤 1-3 之间 → 其他进程因 `/ready` 不存在而拒绝使用配置。若进程看到 `/ready` → 必然已看到所有关联的 `/config` 更新。如果中途宕机，剩余服务器通过 Zab 协议选举新 Leader。新 Leader 同步集群状态，发现 `/ready` 缺失，删除未完成的 `/config` 变更（需应用层逻辑支持），重新执行配置更新流程。

对于第二个问题，解决办法是**异步流水线**，客户端可连续发送多个写请求，无需等待前一个请求完成。ZooKeeper 服务端按 FIFO 顺序处理同一客户端的请求，确保操作线性化，这样减少网络往返（RTT）和等待时间，吞吐量提升 10 倍以上。

第三个问题的处理办法是**sync请求**：当sync之后有一个read操作时，它俩会构成一个慢读取操作。sync使一个服务器在执行read操作之前会执行所有被挂起的write请求，而没有一个完整写的开销。

ZooKeeper 还具有以下两个可用性和持久性保证：

- 如果半数以上的 ZooKeeper 服务器是活跃的，则集群服务是可用的；
- 如果ZooKeeper 服务成功地响应了改变状态的请求，那么只要失败的服务器是可恢复的，则该变更就会在任何数量的故障服务器中被持久化。

#### ZooKeeper的应用（IMPORTANT！）

所有原语均基于以下核心机制：

- **临时节点（Ephemeral Nodes）**：自动清理失效会话的节点，用于状态与生命周期绑定（如锁、组成员管理）。
- **顺序节点（Sequential Nodes）**：生成全局唯一递增序号，用于公平调度与避免竞争（如无惊群锁）。
- **Watch 机制**：事件驱动通知，减少轮询开销，实现高效等待。
- **原子性操作**：节点创建、删除等操作的原子性保证。

##### 配置管理

对于配置管理而言，会单独创建一个Znode节点，存储信息，所有集群单体启动时都要访问一下这个节点，并且设置一个监听，如果内容修改，ZooKeeper会通知所有设置了监听的集群单体，所有正在节点都会收到信息修改的监听信号。集群单体在收到信号后，重新去读取最新的配置，并且在读取时再次设置监听，为接收下一次变更做准备。

它的核心思想是利用 **Watch 机制**实现“发布-订阅”模式，避免轮询，实现配置的实时动态更新。

##### 汇合

客户机可能想要启动主进程和几个工作进程，但是启动进程是由调度程序完成的，因此客户机不知道在时间之前的信息，诸如地址和端口，这些用来给予worker进程连接到主设备的信息。对于这种情况，解决办法如下：
1. 首先Zookeeper设置一个公共的，已知且固定的节点，这个进程是所有节点都知道的。
2. Master启动之后，将自己的具体连接信息（IP地址、端口号）写入这个节点。
3. Worker 启动后，它也只知道要去这个固定节点找信息。
4. Worker节点读取信息，如果读取到了，就进行连接，如果没读取到，则设置一个watch监听，然后等待被通知，当Master将信息写入这个节点之后，这个监听就会收到信号。
5. Worker 收到信号，再次去读取节点，就拿到地址了，可以按照读取到地址的方式来处理。

##### 群组关系

要想知道当前有哪些进程在正常运行，对于Zookeeper的实现方式如下：
1. 我们创建一个永久的“群”节点，比如 `/WeChatGroup`。
2. 每个进程（群成员）加入时，在 `/WeChatGroup` 下面**创建一个临时子节点**，比如 `/WeChatGroup/member1`, `/WeChatGroup/member2`。节点里可以存自己的信息（比如IP地址）。
3. 任何一个进程，只要通过 `getChildren(/WeChatGroup, watch=true)` 获取子节点列表，就能知道所有在线的成员。
4. **关键妙用**：如果某个进程崩溃或断线了，因为它创建的是**临时节点**，这个节点会自动消失。其他监听了 `/WeChatGroup` 的进程会立刻收到“子节点变化”的通知，从而更新成员列表。

它的核心思想就是利用临时节点来反映进程的存活和运行状态。

##### 简单锁

这个就有点类似Go里面的mutex的lock，这里不多说。但是会有惊群效应，就是一个锁解锁之后，会有大量的节点冲过来去抢一个空位，导致内存或者其他资源浪费。

##### 无惊群效应的简单锁（Simple Locks without Herd Effect）

这个的本质就是利用顺序节点的序号来实现一个先后顺序的取锁，避免了惊群效应。具体过程如下：
1. 每个想获得锁的客户端，都在一个锁节点（比如 `/lock`）下**创建一个临时顺序节点**。假设创建了：`/lock/lock-000001`, `/lock/lock-000002`, `/lock/lock-000003`。
2. 客户端获取 `/lock` 下的所有子节点，并按顺序排列。
3. 如果自己创建的节点是序号最小的那个（比如 `lock-000001`），那么恭喜，你获得锁，可以“进入卫生间”了。
4. **如果不是第一个**
    - 客户端**不监听根节点 `/lock`**（否则任何人释放锁都会惊动所有人，造成“羊群效应”）。
    - 相反，它**只监听排在自己前面的那一个节点**。比如，持有 `lock-000002` 的客户端只监听 `lock-000001`；持有 `lock-000003` 的只监听 `lock-000002`。
5. 当前面的节点被删除（意味着前一个使用者释放了锁）时，ZooKeeper 会通知你。
6. 你醒来，回到第2步（“看叫号屏”），重新检查自己是不是当前最小的节点。如果是，获得锁；如果不是，就继续监听新的“前一个节点”。

##### 读写锁

其实简单来讲就是两点。

- **共享读（Shared Read）**：多个客户端可以**同时**读取数据，互不干扰。
- **独占写（Exclusive Write）**：同一时间只能有**一个**客户端写入数据，并且在写入时，不允许任何客户端读取或其他客户端写入。

##### 双重屏障

让一组进程同时开始一个任务，并且等都结束后再一起离开。它的原理是利用**子节点数量**和**监听机制**来同步一组进程的进入和离开状态。这里用一场赛跑为案例解释。所有运动员（进程）需要在起跑线（进入屏障）准备好，听到发令枪后**同时开始**。所有运动员都冲过终点线后（离开屏障），比赛**同时结束**。具体过程如下：

1. 创建一个屏障节点 `/race`。
2. 每个运动员在 `/race` 下创建一个临时子节点（如 `/race/runner1`）。
3. 运动员监视 `/race` 的子节点数量。当子节点数量达到预设的运动员总数时，说明大家都准备好了，可以开始赛跑（执行计算任务）。
4. 计算完成后，运动员删除自己的子节点。
5. 运动员监视 `/race` 的子节点。当子节点数量变为0时，说明所有人都跑完了，可以一起进行下一步。

### ZooKeeper的应用

#### 1. **爬取服务（Fetching Service, FS）**

- **应用场景**：雅虎搜索引擎的分布式爬虫系统，负责抓取数十亿网页。
- **ZooKeeper 核心用途**：
    - **主节点选举**：通过 ZooKeeper 选举主进程（Master），确保主节点故障时快速切换。
    - **配置管理**：主节点向抓取器（Fetcher）动态分发抓取配置（如目标 URL 规则、频率限制）。
    - **状态监控**：抓取器将运行状态与健康信息写入 ZooKeeper，实现故障检测与自动恢复。
- **流量特征**：读操作（`GetData`、`Exists`）频率远高于写操作（读写比 10:1 至 100:1），符合配置频繁读取、状态周期性上报的特点。

---

#### 2. **Katta（分布式索引器）**

- **应用场景**：非雅虎生态的分布式索引服务，用于大数据分片与并行处理。
- **ZooKeeper 核心用途**：
    - **分片分配**：主节点（Master）通过 ZooKeeper 管理数据分片到从节点（Slave）的分配逻辑。
    - **故障恢复**：监控 Slave 节点存活状态，自动重新分配故障节点的分片。
    - **主节点容灾**：通过 Leader 选举机制实现主节点故障时无缝切换，保障服务连续性。
- **设计优势**：解耦任务调度与节点状态，实现高可用与弹性扩展。

---

### 3. **雅虎消息代理（Yahoo! Message Broker, YMB）**

- **应用场景**：高可靠分布式发布-订阅系统，支持数千主题的消息路由。
- **ZooKeeper 核心用途**：
    - **主题分布管理**：记录每个消息主题的主备服务器信息（如 `topics/topic1` 的 `master` 与 `backup`）。
    - **服务器状态监控**：通过**临时节点**（Ephemeral Znode）实时跟踪服务器存活状态，自动剔除故障节点。
    - **主备选举**：确保每个主题的主服务器故障时，备份服务器快速接管（如 `leader election`）。
    - **负载与状态同步**：服务器节点动态写入负载信息，支持动态负载均衡。
- **架构特点**：无共享设计依赖 ZooKeeper 实现全局一致性，保障消息可靠性与系统扩展性。
